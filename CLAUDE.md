# Working on Leafdesk

A map of the codebase for whoever works on it next: where things live, the rules the tests enforce
and the traps that cost a round. It sits next to the README and `docs/` instead of repeating them: `docs/development.md`
*Architecture* explains the moving parts, *Development* lists the scripts and e2e files,
*Languages* and CONTRIBUTING.md *Translations* cover texts.

## What it is

A workspace of pages and databases with real-time collaborative editing, AI chat and agents, an
MCP server, a REST API and outbound connections. One Node process (`server.ts`) runs Next.js 16
(App Router) and the Hocuspocus collaboration server; PostgreSQL 18 through Drizzle; Better Auth;
BlockNote on Yjs; Tailwind v4; next-intl. Node 24, pnpm 11. A separate Electron app lives in
`desktop/`, the static website in `site/`.

## Layout

- `server.ts`: boots everything. It imports `src/server/*` only after env is loaded (those modules
  read `DATABASE_URL` at import), routes `/collab` to Hocuspocus and, after `listen`, starts about
  20 background jobs (`start*` calls). A new background job is started there.
- `src/proxy.ts`: per-request nonce CSP (`src/lib/content-security-policy.ts`) and the
  `x-leafdesk-path` header that `src/server/session.ts` reads to come back after sign-in.
- `src/app/`: routes. `w/[workspaceId]/p/[pageId]/page.tsx` is one route for pages, databases and
  rows (`components/page/page-view.tsx`, `components/database/database-page.tsx`,
  `components/database/row-properties.tsx`). `s/[token]` published pages and sites, `f/[token]`
  public forms, `(auth)/` sign-in screens, `api/` route handlers, `mcp/route.ts` the MCP server,
  `api/v1/[[...path]]` the REST API, `scim/v2`, `oauth/consent`, `print`, `admin`, `account`.
- `src/app/actions/*.ts`: server actions, one file per area. Thin: `requireUserId()`, check and
  narrow every argument by hand, call `@/server/*`, return an `ActionResult` shape (`{ ok, data }`
  or `{ ok, error }`, declared in each file), `revalidatePath`. Nothing in `src/server` or `src/lib` imports actions.
- `src/server/`: server-only domain code (by convention; there is no `server-only` import).
- `src/lib/`: mostly pure code shared by client and server (property types, views, filters,
  formulas in `formula/`, markdown, search words, importers in `import/`). Server-only exceptions:
  `auth.ts`, `env.ts`, `client-ip.ts`, `secret-files.ts`, `totp.ts`, `apple-client-secret.ts`; client-only: `auth-client.ts`.
- `src/components/`: React components by area (`page/`, `database/`, `settings/`, `ai-chat/`,
  `sidebar/`, `published/` …). Server components live here too: a file without `"use client"` is
  one, and may import `@/server/*`.
- `src/db/schema/*.ts`: tables, grouped by area (`app.ts` workspaces, pages, properties, views;
  `auth.ts` is generated by `pnpm auth:schema`, don't edit it by hand). `src/db/index.ts` is the one
  connection pool.
- `drizzle/`: migrations and `meta/_journal.json`. `src/i18n/messages/<locale>/*.json`: texts.
- `README.md`: the overview, quick start and the index of `docs/`, where the user and admin
  documentation lives, one file per area (features, self-hosting, AI, agents, REST API …). A
  feature's description goes in the docs file of its area.
- `scripts/`: `migrate.ts`, `*-e2e.ts` end-to-end checks, `bundle-budget.ts`, `ai-eval.ts`,
  `upgrade-test.sh`, `scale-seed.ts` / `scale-e2e.ts`, screenshot and social-preview generators.

## Where each part lives

- **Access.** `src/server/access.ts` is the one place that decides who may see or change a page:
  `requirePageAccess(userId, pageId, level)` for one page, `pageVisibleTo(userId)` as the SQL
  condition for lists. The rule is the SQL function `page_access_level`, last redefined in
  `drizzle/0141_edit_content.sql`. For a database's rows, `childVisibleTo(userId, databaseId)` works it
  out once per database instead of once per row; Postgres JIT can add about 200 ms to such queries,
  so `server/assigned.ts` runs them with `set local jit = off`. Roles: `src/lib/workspace-roles.ts` (`contentRole`: a membership admin
  is a member on content; `managesPeople`, `mayChangeRole`, `mayRemove`); people management checks
  `requirePeopleManager`, while `requireMembership(…, "owner")` stays owner-only. Shares: `permissions.ts`; per-property rules:
  `property-access.ts`; rows giving the people they name access: `row-access.ts`; teamspace
  membership: `teamspaces.ts` (a locked teamspace's top level: `requireArrangeTopLevel`, checked in
  `pages.ts` moves, trash, restore and delete and in `requireTeamspaceForPages`); guests: `guests.ts`. Sign-in policies (approved networks, two-step,
  SSO only) are `policyHold` there; the request's address comes from `CLIENT_IP_HEADER`, which
  `server.ts` sets on requests and on websocket upgrades alike.
- **Page content.** The Yjs document is the source of truth. Writes from the server go through
  `getCollab()` (`src/server/collab/bridge.ts`: `replaceContent`, `editBlocks`, `setTitle` …), which
  only exists when the app runs through `server.ts`. A block whose data is all in its props, written
  while people may be editing (meeting notes), changes them in place with `updateBlockAttributes`:
  `editBlocks` and other `writeBlocks` callers read, await, then rewrite, and can lose edits made
  in between. Editor-side rewrites that must ride along with the change that caused them (toggle headings
  taking their section, `components/page/toggle-headings.ts`; column cleanup) are ProseMirror
  `appendTransaction` plugins that skip transactions carrying `ySyncPluginKey` meta (others' edits
  and undo), so they make one undo step and never run twice. Saves derive markdown and text (`collab/service.ts` `persistPage`) and announce `pageChanged()` (`page-events.ts`); row value
  changes announce through `row-events.ts`. Page tree operations: `src/server/pages.ts`; databases,
  rows and properties: `databases.ts`; formulas and rollups: `derived.ts` (pure part in
  `src/lib/derived.ts`). Row values are checked in `databases.ts` `normalizeRowProperties` (types,
  property access, dependent selects; a place's address is looked up there first, through
  `geocoder.ts`, because the shared `normalizeValue` is synchronous and takes only coordinates); a
  write that stores values another way (`ai-properties.ts` `saveValue`) calls `followOrRefuse` itself.
  A relation's limit to one row (`single`, like a person's), row-page section and the properties
  its linked rows show in chips, that section and the row picker are `src/lib/relation-options.ts`;
  those values ride along in `getRelationTargets`, never a fetch per chip.
  Unique ID numbers are given out by Postgres triggers (`drizzle/0131_unique_id.sql`), never by app
  code: an inserted row always gets the next number (the value it brings is dropped) and an
  update keeps the old one. Copies that must keep their numbers (a duplicated database, a restored
  backup) insert the rows before the property; `server/unique-ids.ts` checks prefixes.
  Grouped lists and galleries share `components/database/view-sections.tsx` (the header is
  `GroupHeader` in `group-label.tsx`, also a board's sub-group); a board's sub-groups
  (`subGroupBy`) use the default date and status grouping. A new property-id field of `ViewConfig`
  goes into `lib/duplicate.ts` (`remapViewConfig`, `dropPropertyReferences`),
  `lib/convert-property.ts` `retypeViewConfig` and `lib/views.ts` `layoutConfigError`.
  Several linked databases at once (views, example rows, an intro page) are a plan: checked in
  `src/lib/database-plan.ts`, created all-or-nothing by `database-plan.ts` `createFromPlan`, which
  Build with AI (`ai-build.ts` drafts the plan) and the AI chat's `create_database` both use.
- **Legal holds.** `src/server/legal-hold.ts` is the one check before content is deleted for good
  (Delete forever, trash and history retention, file cleanups, templates, deleted properties,
  comments, letterheads, workspace and account deletion). A new hard delete of pages, rows, files
  or what people wrote calls it; moving to the trash doesn't need to.
- **Shared operations.** `src/server/operations.ts` is what the MCP tools, the REST API, the AI
  chat, agents and automations do with pages, databases, rows and comments. Each operation runs as
  `ctx.userId` with that person's access; the caller checks its own scopes first.
- **MCP server.** Every tool is registered in `src/server/mcp/tools.ts` `createMcpServer`; tools
  without `readOnlyHint: true` are treated as writes. Scopes: `mcp/principal.ts`. Large or rarely
  needed inputs (filters, view settings, widgets, automation steps, row values) show only an
  outline and a `leafdesk://docs/<topic>` pointer (`mcp/docs.ts` `checked`, `see`) and are checked
  in full when called; the topics are MCP resources written from the strict zod schemas, also read
  by `get_page`. Related writes of the same risk share one tool with an `action` (`change_memory`,
  `set_agent_schedule`); keep reads and writes in separate tools, since clients ask before writes.
  `ops.inputs` is shared with the REST API's OpenAPI: change MCP's view of an input with `.extend`
  in `mcp/`, not there.
- **REST API.** One route table, `API_ROUTES` in `src/server/api/routes.ts` (`defineRoute`); the
  OpenAPI document is generated from it. Bearer tokens only (`api/tokens.ts`).
- **AI.** `src/server/ai/index.ts` is the only door to the model library: `complete`, `stream`,
  `embed`, `transcribe`, with limits and usage built in. Chat: `ai-chat.ts`; its tools:
  `ai-tools.ts` (writes reuse MCP's checks: form settings in `mcp/form-settings.ts`); CSV files
  attached to questions: `src/lib/chat-attachments.ts` (limits, names) and
  `chat-attachment-table.ts` (the parser, loaded by the box only when a file comes); AI property values: `ai-properties.ts`; notes it keeps: `ai-memory.ts`; semantic
  index and search: `semantic-index.ts`, `semantic-search.ts`. Test doubles: `ai/testing.ts`
  (`installFauxAi`, unit tests) and `ai/fake-openai.ts` (`startFakeOpenAi`, e2e scripts).
- **Search.** `src/server/pages.ts` `searchPages` merges `fullTextSearch` with semantic search;
  `semantic-search.ts` `searchScope` is the one place a search's scope and filters become SQL, used
  by full-text, document and ID hits and by search by meaning alike, so a new filter goes there (and
  into `scoped()` in pages.ts, or it won't list pages without text). The box's typed syntax and
  quoted phrases: `src/lib/search-query.ts`; its filter menus: `src/lib/search-filters.ts` (server),
  `search-filter-state.ts` (import-free, for the box in every first load).
- **Agents.** `src/server/agents/run.ts` is the worker (`agent_run`, its `source` typed in
  `src/lib/agents.ts`) and holds the tool lists; runs are queued from `requests.ts`, `chat.ts`,
  `mentions.ts`, `handoff.ts` and the `agent` schedule kind. Each agent is its own user.
- **Connections** (outbound MCP): `src/server/connections/` (`manage.ts`, `client.ts`, `fetch.ts`
  for the address checks, `events.ts` for inbound events, `approvals.ts`). The catalog of
  ready-made services is `src/lib/connection-catalog.ts`; `pnpm catalog:check` probes it live.
- **Automations and schedules.** `src/server/automations/` (queued from `databases.ts` after row
  writes; `asAutomation` keeps an automation's writes from firing more automations) and
  `src/server/schedules.ts` (`registerScheduleHandler`).
- **Other areas:** meeting notes `meetings.ts` (the block's props, `src/lib/meetings.ts`; its list
  table synced in `persistPage` by `meeting-notes.ts`), sprints `sprints.ts` (no table: the setup is the `sprints` config on the task database's relation
  with role `sprint`; the current sprint's views filter on a hidden rollup of the sprint state, so
  they follow a completion without changing; rollups show option names, so `updateProperty`
  rewrites such rollup filters when options are renamed), Telegram bot `src/server/telegram/`, synced databases (own
  `database_sync` table, `source` jira or github; the runs and the one-minute sweep are
  `jira-sync/run.ts` for both, rows written by `synced-rows.ts`; Jira in `jira-sync/` and
  `src/lib/jira-sync.ts`, GitHub pull requests in `github-pulls/` and `src/lib/github-pulls-sync.ts`,
  people matched by their `account` with provider github), GitHub pull requests moving tasks `github-sync/` (deliveries handled in the request at `api/github/[syncId]`; pure
  ID matching and the status rule in `src/lib/github-sync.ts`), the Send to Slack step's address
  check and message in `src/lib/slack.ts`, mail to and from rows `row-mail/`, follow-up
  sequences on rows `sequences/` (sent by a 30-second `startSequences` job; `runSequences(now)` runs
  a round as of any moment, which `scripts/follow-ups-e2e.ts` uses), page webhooks
  `page-webhooks/` (queued from `pages.ts`, `collab/service.ts` and `comments.ts`, sent as the owner
  who last saved the webhook; `runPageWebhooks(now)`), audit log streaming `audit-stream.ts` (an outbox a trigger on `audit_event` fills, so
  events committed out of order still go; `runAuditStreams(now)`), sensitive content scans
  `sensitive-content.ts` (detectors and masking pure in `src/lib/sensitive-content.ts`; a sweep
  reads pages whose `updated_at` moved past `sensitive_scan`), verified pages `verification.ts`
  (`activeVerification` is the SQL for search and lists; `runVerificationReminders(now)`), named
  page versions `page-versions.ts` (`page_snapshot.name`; `retention.ts` `pruneSnapshots` never
  deletes a named one; listing, preview and restore stay in `pages.ts`), SMTP
  `mail/`, inbox `notifications.ts`, push `push.ts`, files `files.ts` + `storage/` (local, S3,
  workspace drives), import `import/` (TextBundles: `lib/import/textbundle.ts` turns each into a Markdown file of the upload;
  OneNote and other `.mht` files: `lib/import/mhtml.ts` reads the MIME parts, `mhtml-convert.ts` the HTML; a web page: `web-clip.ts`, fetched through `connections/fetch.ts` with `{ web: true }`, read by
  `web-clip-extract.ts`, recipes by `src/lib/recipe.ts`), export `export.ts`, server-made PDFs `pdf.ts` (reads a page like `print.ts`; `export-pdf.ts` zips one per page for the workspace export)
  and `pdf-document.ts` (pure pdfmake layout; pdfmake must stay in `serverExternalPackages` in
  `next.config.ts`, bundled it loses its font files, and its fonts in the standalone build's
  `outputFileTracingIncludes`; CJK text goes to the system's Noto Sans CJK, found in `pdf.ts` and
  installed by the Dockerfile, through `withCjkFont`), PDF letterheads `letterheads.ts` (pure part in `src/lib/letterheads.ts`;
  the logo is document content kept in `pdf_letterhead`, not page decoration), backup `backup/`, SSO `sso.ts`, SCIM
  `scim.ts`, sealed secrets `secret-box.ts`.
- **Editor odds and ends.** Media alignment and in-place width: `lib/media-blocks.ts` (file and
  audio specs shared with the server) and `lib/media-placement.ts` (pure; published pages use it).
  Shiki ships no grammar for some languages: `lib/code-grammars.ts` holds small ones (patterns as
  RegExp objects with flags `dgu`; the precompiled engine compiles no strings). Downloads of files
  on other sites go through `app/api/files/external` (connections' address checks only). Comment
  mentions and previews: `lib/comment-refs.ts`, resolved per reader by `server/comment-refs.ts`.
  Cmd/Ctrl+Alt+T: `components/toggle-all.ts` (views with groups join through `useToggleAllGroups`).
  Dictation at the caret: `components/page/dictation.tsx` (phases in `lib/dictation.ts`; recording,
  the transcribe request and one-dictation-at-a-time shared with the chat in `voice/dictation.ts`).
  A place kept across async work is a Yjs relative position (`ai-assist.tsx` does the same): others'
  edits reach ProseMirror as whole-document replacements, so a ProseMirror mapping doesn't follow them.
  Nested numbered lists count 1, a, i by depth (`lib/list-markers.ts`): the editor adds
  `data-marker` beside BlockNote's `data-index` (`components/page/list-markers.ts`), published pages
  style nested `<ol>`, `pdf-document.ts` passes the depth down.
  Quotes have a `size` prop (`lib/quote-block.ts`, in both schemas); a large one is written with
  `<!-- leafdesk:large-quote -->` before it, like a callout's `no-print` marker; new quotes take the
  size last picked (`components/page/quote-size.ts`, an `appendTransaction` plugin reusing
  `changedRanges` from `toggle-headings.ts`).
  What tables offer (merging, cell colors, headers) is `TABLE_SETTINGS` in `embed-blocks.tsx`, for
  every editor that shows tables. A prop added to one of BlockNote's own blocks (a quote's size, a
  code block's caption) goes in one config in `lib/` (`quote-block.ts`, `code-block.ts`) that the
  editor's spec and `server/blocknote.ts` both use: the side that doesn't know a prop drops it.
  BlockNote's own Backspace runs before a plugin's `handleKeyDown`:
  an extension that must see Backspace first takes it in `keyboardShortcuts` (`smart-quotes.ts`).
- **Icons.** A stored icon is an emoji or `icon:<name>[:<color>]` (`src/lib/icon-value.ts`, tiny and
  safe anywhere; checked by `lib/icon.ts` `parseIcon` against `lib/builtin-icon-names.ts`). Show one
  with `IconGlyph` (`components/builtin-icon.tsx`), never as raw text; text output strips it with
  `iconText`. Drawings (`lib/builtin-icons-data.ts`, from `scripts/builtin-icons.ts`) load lazily;
  server SVG for favicons and PDF is `lib/builtin-icon-svg.ts`. Emoji data and names per locale are
  static files in `public/emoji/` written by `scripts/emoji-data.ts`, fetched by the picker and the
  editor's ":" menu, never imported.
- **Reports about published pages** (`server/page-reports.ts`, table `page_report`): the form is
  its own route, `s/[token]/report`, on the app's address like `duplicate` (a site's domain
  redirects there, `routeOnSiteHost`); `servedPublication` decides whether the page is served.
  Owners get the `page_reported` inbox kind (an OWNER_KIND) and the list in Settings → Security.
- **Dates typed in words.** `src/lib/date-words.ts` holds each language's date words and reads
  dates in tokens (quick add, `lib/quick-add.ts`, finds them inside a row's title);
  `lib/date-phrase.ts` `parseDatePhrase` reads a whole phrase (times, durations, `+2w` from the
  day shown) for `@`, the date property editor, date mentions and date filters. A new place where
  a date is typed uses `components/date-phrase-input.tsx`, which loads the grammar on the first keystroke.
- **Published links can expire** (`page_publication.expires_at`): every query that serves or
  lists a publication to visitors adds `livePublication()` (`src/server/publication-live.ts`, its own
  module so `mentions.ts` can use it without an import cycle); there is no job that unpublishes.
  `getPublishedPage`, `anyPagePublished` (files), `site.ts` and `mentions.ts` do; a new public read
  must too. Page audit events get `details.audience` in `recordAudit` (`server/page-audience.ts`).
- **Workspace sites** (`site.ts`, routes `src/app/s/`): a site on its own domain is routed by
  `server.ts` through `site-hosts.ts`, which sets the trusted `x-leafdesk-site-host` /
  `x-leafdesk-site-analytics` headers (dropped from every client request) that `proxy.ts` rewrites
  and widens the CSP by. The analytics header is only ever set on the site's own domain: never
  load a third-party script on the app's address, where session cookies live. Only what `routeOnSiteHost` (`src/lib/site.ts`) lets through is served on
  such a host; a path a published page needs there (a new file route) goes into it, and a path
  left out of the proxy's matcher is not rewritten to the site there.

**Running as a person.** Every operation carries a real user id and access is worked out in SQL
when it runs, never carried over from earlier. On top of that, AsyncLocalStorage overlays:
`runAsConnectedApp` (MCP, REST, Telegram: the workspace's connected-apps setting applies instead
of sign-in policies), `runActingFor` (an agent acting for a member gets the lower of both
accesses), `asAutomation`. Background work runs as a stored person and is checked again when it
runs: automations as whoever last saved them, schedules as whoever last set them, agents held to
the person in the run's source.

**Background jobs.** Two patterns: `startSweep(everyMs, work)` (`src/server/sweep.ts`, one run at a
time) and DB-backed queues that claim rows with `for update skip locked` (agents, automations,
schedules). State shared between Next's bundle and `server.ts` lives on `globalThis.__leafdesk*`,
because they are separate module graphs.

## Rules the tests enforce

- `src/server/access.test.ts`: only access, workspaces, permissions, guests, join-requests,
  teamspaces, scim, groups and `backup/tables.ts` may mention `workspace_member` /
  `workspaceMember`, even in a comment; only teamspaces and `backup/tables.ts` may mention
  `teamspace_member`. A per-person-per-workspace preference gets its read/write function in
  `workspaces.ts` (like `getSidebarLayout`) and others call that.
- `src/server/backup/tables.test.ts`: every new table goes into `BACKED_UP` or `LEFT_OUT` in
  `src/server/backup/tables.ts`.
- `src/i18n/messages.test.ts`: every locale has every English key with the same placeholders
  (`pnpm i18n:check`); a `"use client"` file may not use `settings.audit` texts (they are not sent
  to the browser).
- `src/lib/search-words.test.ts`: `CJK_RANGES` matches the latest migration that defines
  `cjk_bigrams`. `src/lib/offline.test.ts`: `public/sw.js` follows `src/lib/offline.ts`.
  `src/lib/connection-catalog.test.ts`: `public/connections/*.png` matches the catalog.
  `src/lib/contrast.test.ts`: colors in `globals.css` keep their contrast.
- `src/lib/settings-search.test.ts`: every entry of the settings search (`src/lib/settings-search.ts`)
  names English texts that exist and a group or row marked `anchor="<id>"`, and every settings tab
  has one. A new setting gets an entry there, with the condition the page shows it under.
- `src/server/mcp/tools-context.test.ts`: the MCP tool list every client sends its model stays
  under 90 tools, 165 KB in all and 12 KB per tool. Raise a number only on purpose, in the same
  commit; first move what a model needs only now and then into a docs topic.
- `scripts/bundle-budget.ts` (CI, after `pnpm build`): gzipped client JS budgets for the largest
  route's first load, all routes' first-load chunks together and the largest on-demand chunk. Lazy
  code has no total. Anything in `src/app/w/[workspaceId]/layout.tsx`'s static imports (sidebar,
  row panel, AI chat) is in every workspace route's first load: load editors, views and occasional
  dialogs there with `lazy`/`dynamic`. Small shared modules reached from there (`lib/mentions.ts`
  through `block-focus.ts`) are copied into several route chunks, so every byte added to them counts
  about four times: put new helpers in a module of their own (`lib/link-mentions.ts`). Raise a
  budget only on purpose, in the same commit.

## Conventions

- **Texts.** No user-facing string in code. Add the key to `src/i18n/messages/en/<ns>.json` and to
  every other locale (CONTRIBUTING *When English changes*); a new namespace file also needs a line
  in `src/i18n/messages/en.ts`. ICU MessageFormat; keys are type-checked. Client components use
  `useTranslations`, server code `getTranslations` from `next-intl/server`.
- **Schema and migrations.** Change `src/db/schema/*`, then `pnpm db:generate`. Hand-written SQL
  (functions, triggers) goes after the generated statements behind `--> statement-breakpoint`, or
  in `drizzle-kit generate --custom --name <name>`. The server never migrates on start: run
  `pnpm db:migrate` (Docker runs it before the server). Never edit a migration's SQL once it has
  shipped, not even a trailing newline: databases record its hash, and the upgrade test
  (`scripts/upgrade-test.sh`) fails when the file no longer matches.
- **Renumbering a migration** after a parallel branch took the number: rename the file, its journal
  tag and the snapshot `id`/`prevId` chain, and keep `when` in `_journal.json` increasing
  (`max(now, previous + 1)`). Drizzle skips a migration whose `when` is older than the last applied
  one, silently, on existing databases only.
- **`updated_at`.** Tables with `$onUpdate` (`grep -rn 'onUpdate' src/db/schema`) get a new
  `updated_at` on every Drizzle `update()`. To leave a row exactly as it was (restores, repairs),
  write raw SQL with `tx.execute(sql\`…\`)`.
- **Styling.** Use the tokens in `src/app/globals.css` (`bg-bg`, `text-fg-muted`, `border-border`,
  `bg-accent` …) and the `dark:`, `rtl:` and `high-contrast:` variants. `src/components/ui.tsx` is a
  client module: server components may render its components but must not call `cn()` from it
  (they keep a local `cn`).
- **Rendering cost.** Per-row and per-card components don't call `useRouter`, `useSearchParams` or
  `usePathname`: in Next 16 they re-render on every URL change, `?row=` included. The router is
  read once in `database-page.tsx` and handed down; a card asks `useIsOpenRow`
  (`components/database/row-panel-context.ts`). Views are memoized; keep their props stable
  (`src/lib/keep-unchanged.ts` keeps unchanged row objects across refetches).
- **Page decoration** (the page background and cover, and anything like them added later) never loads a
  URL or image a person supplies: only colors, patterns and cover gradients written in the stylesheet
  (`src/lib/page-background.ts`). File and image blocks are content, not decoration.
- **Better Auth hooks** (`src/lib/auth-options.ts`): a `before` hook's returned `body` is merged
  into the request body, so leaving a key out doesn't remove it; `delete` it from `ctx.body`.
- **New server env var:** add it to `src/lib/env.ts`, `.env.example` and the `app.environment` list
  in `docker-compose.yml`. Desktop local mode passes only the variables in
  `desktop/src/local-server.ts`. A new runtime CLI script must be added to the `COPY scripts/…`
  line in `Dockerfile`.
- **Tests.** Unit tests are `foo.test.ts` next to `foo.ts` (Vitest, node environment, no database:
  they mock `@/db`). E2E scripts run against a real database: copy the shape of
  `scripts/api-e2e.ts` (`export {}`, `process.loadEnvFile()`, then dynamic `await import("@/…")`,

## Running and checking

Setup and scripts: `docs/development.md` *Development*. Before calling a change done, run what CI runs:

```bash
pnpm typecheck && pnpm lint && pnpm test && pnpm build && pnpm tsx scripts/bundle-budget.ts
```

plus the `scripts/*-e2e.ts` of the area you touched (`pnpm tsx scripts/<name>-e2e.ts`).
`pnpm lint` fails on warnings. `pnpm test` includes the translation check.

- **Needs a running server** (`pnpm start` or `pnpm dev`): health, mcp, auth (and Mailpit), api,
  columns, export, print, site, scim, security, security-switches, ip-allowlist, two-factor, account, admin (signs
  everyone out), sso (with a mock identity provider; see its header), scale.
- **Needs no server on the same database**, because a server's workers would take the queued work:
  agents, agent-api, agent-approvers, agent-chat, agent-handoff, agent-memory, agent-mention,
  agent-schedule, agent-sharing, agent-skills, automation, button, timed-automation, schedule,
  row-activity, row-follow, row-mail, discussions, follow-ups (starts its own GreenMail container
  unless given ports), page-watch, page-webhooks, verify, wins-log, jira-sync, github-pulls-sync, sprints. `connector-e2e` starts its own `next dev` against
  `<database>_peer`, which must exist; no other dev server may run in the same checkout.
- Each script's header says what it needs. `.github/workflows/ci.yml` shows the env each step gets;
  not every e2e script is in CI.
- On macOS, `HOSTNAME=localhost` binds only `::1`, while the server fetches its own JWKS from
  `127.0.0.1` (`internalUrl()` in `src/lib/env.ts`): MCP then answers 401 "no token payload". Leave
  `HOSTNAME` unset or use `127.0.0.1`.
- `desktop/` is its own pnpm project with its own lockfile: `cd desktop && pnpm install`.

**Releases.** The version is in `package.json`, `site/index.html` and example strings in
`.env.example`, `README.md` and `.github/workflows/{docker,desktop}.yml`; find them with
`git grep -n '<old version>' -- ':!CHANGELOG.md' ':!pnpm-lock.yaml' ':!drizzle'`. A release heading
`## X.Y.Z — date` starts with `### Upgrading from <previous>` (migration range, compose changes,
new settings). Publishing a GitHub release builds the Docker image and the desktop installers.

## Don't name the products we take ideas from

Commit messages, pull request descriptions, code comments and changelog entries describe what
Leafdesk does on its own terms. They never mention Notion or any other product a feature was
modelled on or compared with ("like Notion", "Notion-style", "matches Notion's colors").

Naming another product is fine only where Leafdesk actually works with it: the Notion importer,
connectors and integrations, and the trademark notice in the README and on the website.
