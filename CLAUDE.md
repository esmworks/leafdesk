# Working on Leafdesk

A map of the codebase for whoever works on it next: where things live, the rules the tests enforce
and the traps that cost a round. It sits next to the README and `docs/` instead of repeating them: `docs/development.md`
*Architecture* explains the moving parts, *Development* lists the scripts and e2e files,
*Languages* and CONTRIBUTING.md *Translations* cover texts.

## What it is

A workspace of pages and databases with real-time collaborative editing, AI chat and agents, an
MCP server, a REST API and outbound connections. One Node process (`server.ts`) runs Next.js 16
(App Router) and the Hocuspocus collaboration server; PostgreSQL 18 through Drizzle; Better Auth;
BlockNote on Yjs; Tailwind v4; next-intl. Node 24, pnpm 11. A separate Electron app lives in
`desktop/`, the static website in `site/`, the browser extension (plain JS, no build; it only opens
`/share`) in `extension/`.

## Layout

- `server.ts`: boots everything. It imports `src/server/*` only after env is loaded (those modules
  read `DATABASE_URL` at import), routes `/collab` to Hocuspocus and, after `listen`, starts about
  20 background jobs (`start*` calls). A new background job is started there.
- `src/proxy.ts`: per-request nonce CSP (`src/lib/content-security-policy.ts`) and the
  `x-leafdesk-path` header that `src/server/session.ts` reads to come back after sign-in.
- `src/app/`: routes. `w/[workspaceId]/p/[pageId]/page.tsx` is one route for pages, databases and
  rows (`components/page/page-view.tsx`, `components/database/database-page.tsx`,
  `components/database/row-properties.tsx`). `s/[token]` published pages and sites, `f/[token]`
  public forms, `(auth)/` sign-in screens, `api/` route handlers, `mcp/route.ts` the MCP server,
  `api/v1/[[...path]]` the REST API, `scim/v2`, `oauth/consent`, `print`, `admin`, `account`.
- `src/app/actions/*.ts`: server actions, one file per area. Thin: `requireUserId()`, check and
  narrow every argument by hand, call `@/server/*`, return an `ActionResult` shape (`{ ok, data }`
  or `{ ok, error }`, declared in each file), `revalidatePath`. Nothing in `src/server` or `src/lib` imports actions.
- `src/server/`: server-only domain code (by convention; there is no `server-only` import).
- `src/lib/`: mostly pure code shared by client and server (property types, views, filters,
  formulas in `formula/`, markdown, search words, importers in `import/`). Server-only exceptions:
  `auth.ts`, `env.ts`, `client-ip.ts`, `secret-files.ts`, `totp.ts`, `apple-client-secret.ts`; client-only: `auth-client.ts`.
- `src/components/`: React components by area (`page/`, `database/`, `settings/`, `ai-chat/`,
  `sidebar/`, `published/` …). Server components live here too: a file without `"use client"` is
  one, and may import `@/server/*`.
- `src/db/schema/*.ts`: tables, grouped by area (`app.ts` workspaces, pages, properties, views;
  `auth.ts` is generated by `pnpm auth:schema`, don't edit it by hand). `src/db/index.ts` is the one
  connection pool.
- `drizzle/`: migrations and `meta/_journal.json`. `src/i18n/messages/<locale>/*.json`: texts.
- `README.md`: the overview, quick start and the index of `docs/`, where the user and admin
  documentation lives, one file per area (features, self-hosting, AI, agents, REST API …). A
  feature's description goes in the docs file of its area.
- `scripts/`: `migrate.ts`, `*-e2e.ts` end-to-end checks, `bundle-budget.ts`, `ai-eval.ts`,
  `upgrade-test.sh`, `scale-seed.ts` / `scale-e2e.ts`, screenshot and social-preview generators.

## Where each part lives

- **Access.** `src/server/access.ts` is the one place that decides who may see or change a page:
  `requirePageAccess(userId, pageId, level)` for one page, `pageVisibleTo(userId)` as the SQL
  condition for lists. The rule is the SQL function `page_access_level`, last redefined in
  `drizzle/0141_edit_content.sql`. For a database's rows, `childVisibleTo(userId, databaseId)` works it
  out once per database instead of once per row; Postgres JIT can add about 200 ms to such queries,
  so `server/assigned.ts` runs them with `set local jit = off`. Roles: `src/lib/workspace-roles.ts` (`contentRole`: a membership admin
  is a member on content; `managesPeople`, `mayChangeRole`, `mayRemove`); people management checks
  `requirePeopleManager`, while `requireMembership(…, "owner")` stays owner-only. Shares: `permissions.ts`; per-property rules:
  `property-access.ts`; rows giving the people they name access: `row-access.ts`; teamspace
  membership: `teamspaces.ts` (a locked teamspace's top level: `requireArrangeTopLevel`, checked in
  `pages.ts` moves, trash, restore and delete and in `requireTeamspaceForPages`); guests: `guests.ts`. Sign-in policies (approved networks, two-step,
  SSO only) are `policyHold` there; the request's address comes from `CLIENT_IP_HEADER`, which
  `server.ts` sets on requests and on websocket upgrades alike. A person-facing check through a
  helper that skips them (`pageAccessOf`, `findMembership`, `rowMailAccess`) asks `sessionHeldBack`
  too; row email has `requestRowMailAccess`. Every session Better Auth deletes closes its collab
  connections (`session.delete.after` in `lib/auth.ts`); one deleted with raw SQL needs
  `disconnectEndedSessions`.
- **Page content.** The Yjs document is the source of truth. Writes from the server go through
  `getCollab()` (`src/server/collab/bridge.ts`: `replaceContent`, `editBlocks`, `setTitle` …), which
  only exists when the app runs through `server.ts`. A block whose data is all in its props, written
  while people may be editing (meeting notes, ticking a to-do), changes them in place with
  `updateBlockAttributes` (its `find` gets the block's id, which sits on the `blockContainer`):
  `editBlocks` and other `writeBlocks` callers read, await, then rewrite, and can lose edits made
  in between. Editor-side rewrites that must ride along with the change that caused them (toggle headings
  taking their section, `components/page/toggle-headings.ts`; column cleanup) are ProseMirror
  `appendTransaction` plugins that skip transactions carrying `ySyncPluginKey` meta (others' edits
  and undo), so they make one undo step and never run twice. Saves derive markdown and text (`collab/service.ts` `persistPage`) and announce `pageChanged()` (`page-events.ts`); row value
  changes announce through `row-events.ts`. Page tree operations: `src/server/pages.ts`; databases,
  rows and properties: `databases.ts`; formulas and rollups: `derived.ts` (pure part in
  `src/lib/derived.ts`). Row values are checked in `databases.ts` `normalizeRowProperties` (types,
  property access, dependent selects; a place's address is looked up there first, through
  `geocoder.ts`, because the shared `normalizeValue` is synchronous and takes only coordinates); a
  write that stores values another way (`ai-properties.ts` `saveValue`) calls `followOrRefuse` itself.
  A relation's limit to one row (`single`, like a person's), row-page section and the properties
  its linked rows show in chips, that section and the row picker are `src/lib/relation-options.ts`;
  those values ride along in `getRelationTargets`, never a fetch per chip.
  Unique ID numbers are given out by Postgres triggers (`drizzle/0131_unique_id.sql`), never by app
  code: an inserted row always gets the next number (the value it brings is dropped) and an
  update keeps the old one. Copies that must keep their numbers (a duplicated database, a restored
  backup) insert the rows before the property; `server/unique-ids.ts` checks prefixes.
  Unique values (`options.unique`) are kept by Postgres too (`drizzle/0149_unique_values.sql`,
  table `unique_value`): a write repeating another live row's value fails with 23505 on
  `unique_value_key_idx` (on `md5(key)` since 0151; the triggers raise the readable detail first),
  which `withUniqueValues` (`server/unique-values.ts`) turns into a `PropertyValueError`; wrap a new
  row write in it. A batch (paste, import, sync) calls `dropRepeatedValues` before writing
  (`checkRows` does), so it never stops partway.
  A table's header row is a `<table>` of its own in a sticky box above the rows' box (that box
  scrolls sideways, so `sticky` inside it would hold to it, not the page); the two follow each
  other's `scrollLeft`, and the rows' table keeps a zero-height header row for screen readers and
  as `useTableWindow`'s `start`. The view bar (tabs, toolbar) scrolls away; only the header row
  sticks, under the page's top bar, and paints a background only while stuck
  (`components/use-stuck-mark.ts`), so a page's pattern shows through at rest.
  Grouped lists and galleries share `components/database/view-sections.tsx` (the header is
  `GroupHeader` in `group-label.tsx`, also a board's sub-group); a board's sub-groups
  (`subGroupBy`) use the default date and status grouping. A new property-id field of `ViewConfig`
  goes into `lib/duplicate.ts` (`remapViewConfig`, `dropPropertyReferences`),
  `lib/convert-property.ts` `retypeViewConfig` and `lib/views.ts` `layoutConfigError`.
  A view with `ownerId` is that person's alone: a new read of views adds `viewOwnedBy(userId)`
  (`databases.ts`), and published or copied views take only `ownerId is null`.
  Pivot views: `lib/pivot.ts` (pure; totals measure the rows they cover, never the cells added
  up), one table `components/database/pivot-table.tsx` for the app, published pages and print,
  `server/pivot-text.ts` for server-made files (PDF, the view's CSV/HTML download).
  Agenda views: `lib/agenda.ts` (pure: sections, done, moving dates), one database's rows only,
  `components/database/agenda-view.tsx`; adding one opens `agenda-setup-dialog.tsx` first (date,
  done and priority properties). MCP takes `statusBy`, `priorityBy` and `showUndated` in one
  `agenda` object (docs topic `views`), which keeps the tool list in its budget.
  Several linked databases at once (views, example rows, an intro page) are a plan: checked in
  `src/lib/database-plan.ts`, created all-or-nothing by `database-plan.ts` `createFromPlan`, which
  Build with AI (`ai-build.ts` drafts the plan) and the AI chat's `create_database` both use.
- **Database history.** `src/server/database-changes.ts` records it (table `database_change`):
  the schema writes of `databases.ts` (addProperty, updateProperty, changePropertyType, delete and
  restore of properties and views, addView, updateView …) are thin exported wrappers that run the
  `untracked*` function through `trackSchema`, which reads the properties and views before and
  after. A new schema write gets a wrapper like them; making a new database with its properties
  runs inside `asSetup` (plans, templates, synced databases' setup). Rows trashed and restored
  come from `pages.ts`. Value changes are the rows' `row_activity`, read in groups by
  `server/database-history.ts`, which also undoes entries through the same `databases.ts`
  functions (pure part in `src/lib/database-history.ts`).
- **Legal holds.** `src/server/legal-hold.ts` is the one check before content is deleted for good
  (Delete forever, trash and history retention, file cleanups, templates, deleted properties,
  comments, letterheads, workspace and account deletion). A new hard delete of pages, rows, files
  or what people wrote calls it; moving to the trash doesn't need to.
- **Shared operations.** `src/server/operations.ts` is what the MCP tools, the REST API, the AI
  chat, agents and automations do with pages, databases, rows and comments. Each operation runs as
  `ctx.userId` with that person's access; the caller checks its own scopes first.
- **MCP server.** Every tool is registered in `src/server/mcp/tools.ts` `createMcpServer`; tools
  without `readOnlyHint: true` are treated as writes. Scopes: `mcp/principal.ts`. Large or rarely
  needed inputs (filters, view settings, widgets, automation steps, row values) show only an
  outline and a `leafdesk://docs/<topic>` pointer (`mcp/docs.ts` `checked`, `see`) and are checked
  in full when called; the topics are MCP resources written from the strict zod schemas, also read
  by `get_page`. Related writes of the same risk share one tool with an `action` (`change_memory`,
  `set_agent_schedule`); keep reads and writes in separate tools, since clients ask before writes.
  `ops.inputs` is shared with the REST API's OpenAPI: change MCP's view of an input with `.extend`
  in `mcp/`, not there. A tool refuses an argument it doesn't take (`mcp/strict-arguments.ts`,
  applied to every tool in `createMcpServer`; the list still shows the schema as written), so a
  test or script passing an extra key gets an error.
- **REST API.** One route table, `API_ROUTES` in `src/server/api/routes.ts` (`defineRoute`); the
  OpenAPI document is generated from it. Bearer tokens only (`api/tokens.ts`). `defineRoute` makes
  each query and body schema `.strict()`, so a field a route doesn't name answers 400 (a script
  sending a path's id in the body too gets one).
- **AI.** `src/server/ai/index.ts` is the only door to the model library: `complete`, `stream`,
  `embed`, `transcribe`, with limits and usage built in. The AI chat and agents' chats
  (`components/agent-chat/agent-chat.tsx`) draw questions, steps and message actions with
  `components/ai-chat/message-parts.tsx`, so they stay alike. The panel and the full-page chat
  show one `useChat` held in `AiChatProvider` (`useSharedChat`). An answer runs apart from its
  request (`ai-chat-runs.ts`, keyed by a run id the browser picks): closing the request only stops
  following it, Stop is `stopChatAction`, and `getConversation`'s `run` is followed again through
  `GET /api/ai/chat?run=`, which replays its events from the `conversation` event (it carries the
  question: the turn is saved only at the end). Chat: `ai-chat.ts`; its tools:
  `ai-tools.ts` (reads refuse arguments their schema doesn't name, `unknownArguments`; writes
  reuse MCP's checks: form settings in `mcp/form-settings.ts`), and every
  other MCP tool through `ai-more-tools.ts` (`find_tools`, `use_tool`: the MCP server in this
  process as the person; `HIDDEN` and `ASKED_EACH_TIME` there; agents' runs use it too, without
  the latter; it imports `mcp/tools` lazily, which reaches `agents/chat` and so `ai-chat`); CSV files
  attached to questions: `src/lib/chat-attachments.ts` (limits, names) and
  `chat-attachment-table.ts` (the parser, loaded by the box only when a file comes); AI property values: `ai-properties.ts`; notes it keeps: `ai-memory.ts`; semantic
  index and search: `semantic-index.ts`, `semantic-search.ts`; related pages under a page rank the
  stored chunks against the page's mean embedding (`related-pages.ts`, no model call). Test doubles: `ai/testing.ts`
  (`installFauxAi`, unit tests) and `ai/fake-openai.ts` (`startFakeOpenAi`, e2e scripts). Web
  calls carry data out: the chat asks before each, and agents' chat, mention and request runs
  before each the person didn't write; schedules' runs read only pages of their task or search
  results and refuse others (`lib/web-calls.ts`); a new outbound tool goes through it. Page writes
  carry data out too: a write of the model's (agent runs, the chat, approved proposals) sets
  `WriteActor.model`, and `writeBlocks` turns its media that would load another site into links
  (`lib/model-media.ts`); a new place a model writes a page sets it. Outside text goes to the model
  through `connections/tools.ts` `externalData`/`frameData` (a frame with a new id each time);
  `ai/index.ts` strips invisible characters from all of it (`lib/invisible-text.ts`).
- **Search.** `src/server/pages.ts` `searchPages` merges `fullTextSearch` with semantic search;
  `semantic-search.ts` `searchScope` is the one place a search's scope and filters become SQL, used
  by full-text, document and ID hits and by search by meaning alike, so a new filter goes there (and
  into `scoped()` in pages.ts, or it won't list pages without text). The box's typed syntax and
  quoted phrases: `src/lib/search-query.ts`; its filter menus: `src/lib/search-filters.ts` (server),
  `search-filter-state.ts` (import-free, for the box in every first load). `#tags` are plain text:
  grammar `src/lib/tags.ts` (in the first load too), read from blocks by `lib/tag-blocks.ts`, indexed
  in `page_tag` by `server/page-tags.ts` (persistPage, copies, backfill queue), marked and suggested
  in the editor by `components/page/tags.ts` and `tag-menu.tsx`.
- **Agents.** `src/server/agents/run.ts` is the worker (`agent_run`, its `source` typed in
  `src/lib/agents.ts`) and holds the tool lists; runs are queued from `requests.ts`, `chat.ts`,
  `mentions.ts`, `handoff.ts` and the `agent` schedule kind. Each agent is its own user. Memory
  (`memory.ts`): runs only propose notes, a proposal with `replacesId` changes that kept note in
  place; a schedule's run reads and leaves `agent_run.handoff`, kept to the same schedule, setter,
  database and task (`sameSchedule`); `agent_memory` inbox items are one per agent and owner,
  moved between runs by `withdrawNotices`. Email:
  drafts on rows wait for review (`email-drafts.ts`); a report to the agent's own `mail_recipients`
  goes out at once from the run's person's mailbox (`send-mail.ts`, through `row-mail/send.ts`
  `sendFromMailbox`). Spending guardrails: `server/ai-limit-notices.ts` (the `ai_limit` inbox
  kind near and at a limit, one row per person and month by a unique index; a new agent spending
  fast is turned off mid-run from `run.ts`), `agents/limits.ts` (requests for a higher limit,
  answered from owners' inboxes), pure part `lib/agent-guardrails.ts`; who creates agents is
  `sharing.ts` `mayCreate` (`agent_creator` when the setting is `chosen`).
- **Connections** (outbound MCP): `src/server/connections/` (`manage.ts`, `client.ts`, `fetch.ts`
  for the address checks, `events.ts` for inbound events, `approvals.ts`). A fetch of an address a
  member or visitor gives passes `{ untrusted: true }`: only `WEB_FETCH_ALLOWED_HOSTS` applies to
  it, never `CONNECTOR_ALLOWED_HOSTS`. Allowed-host lists match through `ssrf.ts` `onHostList` (a
  bare name allows the web's ports only). A synced database's setup checks
  `pages.ts` `requireDatabasePlace` and `sync-setup.ts` limits before any network call, and reads
  other servers' answers through `readBodyLimited`. The catalog of
  ready-made services is `src/lib/connection-catalog.ts`; `pnpm catalog:check` probes it live.
- **Automations and schedules.** `src/server/automations/` (queued from `databases.ts` after row
  writes; `asAutomation` keeps an automation's writes from firing more automations; a total over a
  view crossing a line is `threshold.ts`, its last state in `automation_threshold`, asked to look
  by `queue.ts` `thresholdRowsChanged` after writes and from `pages.ts` trash and restore; a
  button property's click queues the runs of `button_clicked` automations in `server/row-buttons.ts`,
  its label and color are `lib/row-buttons.ts`, and `isAction` keeps it out of filters, sorts and
  calculations; a meeting written up on a row queues `meeting_summarized` runs from
  `meetings.ts` `summarizeMeeting` through `server/meeting-triggers.ts`; a "row added" trigger with
  `filled` waits on a row added untitled until it is filled in, `lib/automations.ts`
  `newRowWaitsUntil`, and `PageView` leaving a row calls `newRowClosed`) and
  `src/server/schedules.ts` (`registerScheduleHandler`).
- **Other areas:** meeting notes `meetings.ts` (the block's props, `src/lib/meetings.ts`; its list
  table synced in `persistPage` by `meeting-notes.ts`; an uploaded file is decoded in the browser
  and sent in a live recording's pieces, `components/voice/meeting-upload-session.ts`), to-dos in
  pages for My tasks `page-tasks.ts`
  (index `page_task` synced in `persistPage`, extraction pure in `src/lib/page-tasks.ts`, merged
  into `assigned.ts` lists as items with `type: "pageTask"`; pages to index later go in
  `page_task_backfill`, which a restore of an older backup fills too), sprints `sprints.ts` (no table: the setup is the `sprints` config on the task database's relation
  with role `sprint`; the current sprint's views filter on a hidden rollup of the sprint state, so
  they follow a completion without changing; rollups show option names, so `updateProperty`
  rewrites such rollup filters when options are renamed), Telegram bot `src/server/telegram/`, synced databases (own
  `database_sync` table, `source` jira, github, ical, gcal, postgres or sheets; the runs and the one-minute sweep
  are `jira-sync/run.ts` for all, rows written by `synced-rows.ts`, errors are `JiraError` codes;
  Jira in `jira-sync/` and `src/lib/jira-sync.ts`, GitHub pull requests in `github-pulls/` and
  `src/lib/github-pulls-sync.ts`, people matched by their `account` with provider github;
  calendars in `ical-sync/` and `src/lib/ical-sync.ts` (the pure .ics reader and repeat rules);
  PostgreSQL tables in `postgres-sync/` (`client.ts` checks the host like `connections/fetch.ts`
  and reads in a read-only transaction) and `src/lib/postgres-sync.ts`; Google Sheets in
  `sheets-sync/` and `src/lib/sheets-sync.ts`, read typed through a workspace's Sheets connection
  (`get_spreadsheet`) as the person the sync runs as, checked by `sheetsAccess` on every run; a
  sheet sync without a key column (`keyColumn` "") finds rows by sheet row number, kept in a hidden
  number key property, and only reads;
  Google Calendar in `gcal-sync/` and `src/lib/gcal-sync.ts` the same way (`list_events`,
  writing with `notificationLevel: "NONE"`, times as the calendar's wall-clock time);
  both write back through `sheets_write` (`server/sync-writes.ts`, fed by `afterRowWrites` and
  title saves in `collab/service.ts`; a run's own writes go inside `fromSync`), and the run writes
  them before reading (sheets: `planWrites`; gcal: `writeBack`), leaving fields still waiting
  out of what it reads; a change asks `startDatabaseSyncs` through `globalThis.__leafdeskSyncsSoon`
  to run within seconds, and `server/sync-write-status.ts` is what the database's toolbar shows),
  GitHub pull requests moving tasks `github-sync/` (deliveries handled in the request at `api/github/[syncId]`; pure
  ID matching and the status rule in `src/lib/github-sync.ts`), the Send to Slack step's address
  check and message in `src/lib/slack.ts`, mail to and from rows `row-mail/`
  (a mailbox signs in with a password or a Google sign-in, `google.ts`; open it through
  `credentials.ts` `withMailCredentials`, which renews the token; a member has up to
  `MAX_MAILBOXES` in a workspace, so a lookup of "their mailbox" adds `mailbox.isDefault`, as
  follow-ups, agents and drafts do), the Mail tab `mail-client/` (the owner's own mail alone,
  `access.ts`; headers indexed by the minute's mailbox sweep, `indexer.ts`, bodies read live through
  `pool.ts` `withImap`, two queued connections per mailbox (lane `open` for clicks, `background`
  for folder reads and loading ahead) kept alive by NOOPs and keyed by its servers and password, never
  `updatedAt`, which the sweep changes; a server can drop one silently, leaving its commands waiting
  minutes for the socket timeout, so work someone waits on passes `within` (closed then, throwing
  `ConnectionLost`, which `readBody` tries once more on a new connection); bodies held a few minutes in memory, `body-cache.ts`, and in
  the tab, `components/mail/mail-cache.ts`; HTML cleaned by `html.ts` into a sandboxed frame; the page is
  `components/mail/`, which changes the address with `history.pushState`, never the router (a server
  round trip per click), and holds moves `MAIL_UNDO_SECONDS` before sending them (a new move goes
  into `MOVES` in `mail-app.tsx`; action `move` takes the folder's id in `to`, checked by
  `movableTo`; a row's right-click menu is `thread-menu.tsx`, a `lazyPart`, as is the selection's bar
  `selection-bar.tsx`; `act` takes a list of threads, sent in `MAIL_MAX_THREADS` pieces); why a message's
  images from other sites load is `lib/mail-images.ts`, decided after the fetch for DMARC, from what
  `images.ts` remembers: messages shown before and trusted senders; `body-cache.ts` keys bodies by
  that reason, so `readBody` and `prefetchBodies` work it out alike or a click reads it again;
  `listMailboxes` starts a mailbox's first read in the background (`firstRead`, one at a time per
  box), and the tab asks again while a box's folders are null; writing: the composer is the
  `?c=new` pane or under a thread, `composer.tsx` with the TipTap editor `mail-editor.tsx` (lazy:
  ProseMirror stays out of the thread's chunk), what a reply starts from `compose-start.ts`, the
  HTML sent cleaned again and turned into its text part by `outgoing.ts`, addresses suggested by
  `contacts.ts`; a mailbox's signature, `mailbox.signature` and `signature_text`, is the editor's
  `Signature` node, a `div[data-signature]` that `outgoing.ts` puts under `-- ` in the text part,
  and row emails start with its text; one pasted with images or tables is kept whole inside
  `div[data-pasted]`, `lib/pasted-signature.ts` (its cleaning rules in `-config.ts`), the editor's `PastedSignature` atom, shown in a
  shadow root by `components/mail/pasted-signature.tsx` and cleaned on its own terms when sent;
  the MIME message is `compose.ts`, drafts live in the
  server's Drafts folder, `drafts.ts`: each save APPENDs anew under the same Message-ID and removes
  the old copy only after, files kept are read back from it by part number; an answer's or forward's
  earlier mail never enters the editor: the server adds it under what is written (`quote.ts`, a
  `.leafdesk_quote` / `.leafdesk_forward` element, from the original the first time and from the
  draft before after that); pictures in the text are the editor's `Picture` node, sent as `cid:`
  parts (`compose.ts` `inlineFiles`, form field `inline`), each uploaded once and carried over from
  the draft saved last by Content-ID, opened again as data URLs marked `data-cid`; a send waits
  `MAIL_UNDO_SECONDS` in memory, `write.ts` `holdMail`, which scripts skip with `sendHeld`), follow-up
  sequences on rows `sequences/` (sent by a 30-second `startSequences` job; `runSequences(now)` runs
  a round as of any moment, which `scripts/follow-ups-e2e.ts` uses), page webhooks
  `page-webhooks/` (queued from `pages.ts`, `collab/service.ts` and `comments.ts`, sent as the owner
  who last saved the webhook; `runPageWebhooks(now)`), audit log streaming `audit-stream.ts` (an outbox a trigger on `audit_event` fills, so

**Running as a person.** Every operation carries a real user id and access is worked out in SQL
when it runs, never carried over from earlier. On top of that, AsyncLocalStorage overlays:
`runAsConnectedApp` (MCP, REST, Telegram: the workspace's connected-apps setting applies instead
of sign-in policies), `runActingFor` (an agent acting for a member gets the lower of both
accesses), `asAutomation`. Background work runs as a stored person and is checked again when it
runs: automations as whoever last saved them, schedules as whoever last set them, agents held to
the person in the run's source.

**Background jobs.** Two patterns: `startSweep(everyMs, work)` (`src/server/sweep.ts`, one run at a
time) and DB-backed queues that claim rows with `for update skip locked` (agents, automations,
schedules). State shared between Next's bundle and `server.ts` lives on `globalThis.__leafdesk*`,
because they are separate module graphs.

## Conventions

- **Texts.** No user-facing string in code. Add the key to `src/i18n/messages/en/<ns>.json` and to
  every other locale (CONTRIBUTING *When English changes*); a new namespace file also needs a line
  in `src/i18n/messages/en.ts`. ICU MessageFormat; keys are type-checked. Client components use
  `useTranslations`, server code `getTranslations` from `next-intl/server`.
- **Schema and migrations.** Change `src/db/schema/*`, then `pnpm db:generate`. Hand-written SQL
  (functions, triggers) goes after the generated statements behind `--> statement-breakpoint`, or
  in `drizzle-kit generate --custom --name <name>`. The server never migrates on start: run
  `pnpm db:migrate` (Docker runs it before the server). Never edit a migration's SQL once it has
  shipped, not even a trailing newline: databases record its hash, and the upgrade test
  (`scripts/upgrade-test.sh`) fails when the file no longer matches.
- **Renumbering a migration** after a parallel branch took the number: rename the file, its journal
  tag and the snapshot `id`/`prevId` chain, and keep `when` in `_journal.json` increasing
  (`max(now, previous + 1)`). Drizzle skips a migration whose `when` is older than the last applied
  one, silently, on existing databases only.
- **`updated_at`.** Tables with `$onUpdate` (`grep -rn 'onUpdate' src/db/schema`) get a new
  `updated_at` on every Drizzle `update()`. To leave a row exactly as it was (restores, repairs),
  write raw SQL with `tx.execute(sql\`…\`)`.
- **Styling.** Use the tokens in `src/app/globals.css` (`bg-bg`, `text-fg-muted`, `border-border`,
  `bg-accent` …) and the `dark:`, `rtl:` and `high-contrast:` variants. `src/components/ui.tsx` is a
  client module: server components may render its components but must not call `cn()` from it
  (they keep a local `cn`). Something fixed to the window's top edge (a side panel, a full-window
  view) starts at `top-(--app-top)`: on macOS the desktop app lays its tab strip over the page
  beside the sidebar, where `components/desktop-tab-strip.tsx` tells it (`desktop/src/windows.ts`).
  Something sticky in the workspace's scrolling `<main>` holds at `top-0`: `<main>` starts below the strip already.
  Something fixed to the window's end edge sits at `inset-e-(--chat-width)` (globals.css), so it stays
  beside the AI chat panel, which `<main>` makes room for; panels beside a page that can't share
  that room (comments, graph, the chat) close each other through `lib/side-panels.ts`.
  A dialog is `Dialog` built from `DialogHeader` (or a `DialogTitle` in the body for a short
  question), `DialogBody` and `DialogFooter` (Cancel `secondary`, the action last); a panel over its
  own shade takes `dialogShadow`.
  A backdrop shading the whole window under a dialog carries `data-window-shade`: that component
  tells the desktop app its color, and the tab strip, which the page can't draw over, takes it too.
  Boxes beside a chat's column on a wide page (the agent's page, the AI chat) are
  `components/side-box.tsx` (layout classes `lib/side-layout.ts`): a container query on the page
  shows them, never the window's width; the AI chat lays them over its list, so its scrollbar stays at
  the edge. The lines to a chat's questions and the button back to its latest are
  `components/chat-navigation.tsx`, loaded lazily: `ChatThread` is in every workspace page's first load.
  A menu or card that must leave a scrolling box is placed by `components/use-placement.ts`
  (`placePanel` in `lib/placement.ts`: below or flipped above, start or end edge, inside the
  window): through `Floating` (`database/floating.tsx`, a portal), `Popover`'s `at` (a point or an
  element), or the hook itself; don't measure and place one by hand.
- **Rendering cost.** Per-row and per-card components don't call `useRouter`, `useSearchParams` or
  `usePathname`: in Next 16 they re-render on every URL change, `?row=` included. The router is
  read once in `database-page.tsx` and handed down; a card asks `useIsOpenRow`
  (`components/database/row-panel-context.ts`). Views are memoized; keep their props stable
  (`src/lib/keep-unchanged.ts` keeps unchanged row objects across refetches).
- **Waiting.** Next runs a tab's server actions one at a time, each after the one before: a read a
  component fires on its own (as it opens, on a timer, as a box fills) goes through `read()`
  (`components/read.ts`, served by `app/api/read`, listed in `READS` there), so it neither waits
  nor holds up what the person clicked; writes stay server actions. An action no client calls
  directly any more has no action id in the build, so an e2e script calling it by id (`actionId`)
  fails with "No id for": call it at `/api/read/<name>` (`callRead`). A dialog, menu or panel whose
  code loads when it first opens is a `lazyPart` (`components/lazy-part.tsx`), not `next/dynamic`
  with `ssr: false` or `lazy()` in a Suspense: React holds back what a boundary reveals until
  300 ms after the last fallback shown anywhere.
- **Page decoration** (the page background and cover, and anything like them added later) never loads a
  URL or image a person supplies: only colors, patterns and cover gradients written in the stylesheet
  (`src/lib/page-background.ts`). File and image blocks are content, not decoration.
- **Better Auth hooks** (`src/lib/auth-options.ts`): a `before` hook's returned `body` is merged
  into the request body, so leaving a key out doesn't remove it; `delete` it from `ctx.body`.
- **New server env var:** add it to `src/lib/env.ts` (AI model settings and limits, `AI_*`:
  `src/server/ai/config.ts` `readAiConfig`), `.env.example` and the `app.environment` list in
  `docker-compose.yml`. Desktop local mode passes only the variables in
  `desktop/src/local-server.ts`. A new runtime CLI script must be added to the `COPY scripts/…`
  line in `Dockerfile`.
- **Tests.** Unit tests are `foo.test.ts` next to `foo.ts` (Vitest, node environment, no database:
  they mock `@/db`). E2E scripts run against a real database: copy the shape of
  `scripts/api-e2e.ts` (`export {}`, `process.loadEnvFile()`, then dynamic `await import("@/…")`,
  a stub or real `registerCollab`, unique ids from `Date.now()`, cleanup at the end).
- **CHANGELOG.** Every user-visible change gets an entry under `## Unreleased` (`### Added` /
  `### Changed` / `### Fixed`), a bold lead sentence, migration numbers and new env vars named.

## Running and checking

Setup and scripts: `docs/development.md` *Development*. Before calling a change done, run what CI runs:

```bash
pnpm typecheck && pnpm lint && pnpm test && pnpm build && pnpm tsx scripts/bundle-budget.ts
```

plus the `scripts/*-e2e.ts` of the area you touched (`pnpm tsx scripts/<name>-e2e.ts`).
`pnpm lint` fails on warnings. `pnpm test` includes the translation check.

- **Needs a running server** (`pnpm start` or `pnpm dev`): health, mcp, auth (and Mailpit), api,
  columns, export, print, site, scim, security, security-switches, ip-allowlist, two-factor, account, admin (signs
  everyone out), sso (with a mock identity provider; see its header), scale.
- **Needs no server on the same database**, because a server's workers would take the queued work:
  agents, agent-api, agent-approvers, agent-chat, agent-copy, agent-handoff, agent-memory, agent-mention,
  agent-schedule, agent-sharing, agent-guardrails, agent-skills, automation, button, row-buttons, timed-automation, schedule,
  row-activity, row-follow, row-mail, web-links, discussions, follow-ups (starts its own GreenMail container
  unless given ports), page-watch, page-webhooks, verify, wins-log, jira-sync, github-pulls-sync, sheets-sync, sprints. `connector-e2e` starts its own `next dev` against
  `<database>_peer`, which must exist; no other dev server may run in the same checkout.
- Each script's header says what it needs. `.github/workflows/ci.yml` shows the env each step gets;
  not every e2e script is in CI.
- On macOS, `HOSTNAME=localhost` binds only `::1`, while the server fetches its own JWKS from
  `127.0.0.1` (`internalUrl()` in `src/lib/env.ts`): MCP then answers 401 "no token payload". Leave
  `HOSTNAME` unset or use `127.0.0.1`.
- `desktop/` is its own pnpm project with its own lockfile: `cd desktop && pnpm install`. A tab leaves the server
  only on a sign-in trip started from one of its sign-in pages (`desktop/src/navigation.ts`); local
  mode signs in only after the server's `{ ready: port }` over IPC; desktop texts go in every
  locale of `desktop/src/strings.ts`.

**Releases.** The version is in `package.json`, `site/index.html`, `extension/manifest.json` and example strings in

## Don't name the products we take ideas from

Commit messages, pull request descriptions, code comments and changelog entries describe what
Leafdesk does on its own terms. They never mention Notion or any other product a feature was
modelled on or compared with ("like Notion", "Notion-style", "matches Notion's colors").

Naming another product is fine only where Leafdesk actually works with it: the Notion importer,
connectors and integrations, and the trademark notice in the README and on the website.
